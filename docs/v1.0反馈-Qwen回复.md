### 完全认同的建议

**1. 砍掉 HybridCache 内存降级层**

说得对。我当初加这个是为了"和 Node 版功能对齐"，但仔细想，这个设计在 Go 版里确实是反模式。原因有三：

- 阶段 2 拆微服务后，每个服务实例有自己的内存缓存，数据不一致问题会被放大
- Redis 挂了，Asynq 也挂了，整个异步链路已经瘫痪，此时缓存降级保住的只是几个列表接口的响应，意义极小
- 引入两层缓存反而增加了调试复杂度（"这个数据到底是从哪层拿的？"）

**修正方案：** 直接用 go-redis，Redis 不可用时返回错误，由客户端决定降级策略（比如前端展示缓存的旧数据）。简单粗暴但正确。

**2. Asynq handler 的幂等 + 超时 + 进度**

```go
// internal/task/handlers.go —— 修正版

func NewAIHandler(ai *ai.Client, db *gorm.DB, storage Storage) asynq.HandlerFunc {
    return func(ctx context.Context, t *asynq.Task) error {
        taskID := t.ResultWriter().TaskID()

        // === 幂等检查 ===
        // Asynq 重试时 handler 会重新执行，先查状态
        var task model.Task
        if err := db.First(&task, "id = ?", taskID).Error; err != nil {
            return fmt.Errorf("task not found: %w", err)
        }
        // 如果已经 completed，直接返回（幂等保护）
        if task.Status == "completed" {
            return nil
        }

        // === 标记 processing ===
        db.Model(&task).Updates(map[string]interface{}{
            "status": "processing", "progress": 5,
        })

        var payload AIGenPayload
        if err := json.Unmarshal(t.Payload(), &payload); err != nil {
            markFailed(db, taskID, "payload 解析失败")
            return fmt.Errorf("unmarshal payload: %w", err)
        }

        // === 超时控制 ===
        // 给 AI 调用设 60 秒超时，避免无限等待
        aiCtx, cancel := context.WithTimeout(ctx, 60*time.Second)
        defer cancel()

        // === 进度更新（用 ResultWriter）===
        t.ResultWriter().Write(mustJSON(map[string]int{"progress": 20}))
        db.Model(&task).Update("progress", 20)

        content, err := ai.Chat(aiCtx, payload.Model, payload.Messages)
        if err != nil {
            // 区分可重试和不可重试错误
            if errors.Is(err, context.DeadlineExceeded) {
                markFailed(db, taskID, "AI 调用超时")
                return fmt.Errorf("ai timeout: %w", err) // 返回 error → Asynq 重试
            }
            markFailed(db, taskID, err.Error())
            return err
        }

        t.ResultWriter().Write(mustJSON(map[string]int{"progress": 90}))

        // === 保存结果（幂等：用 taskID 命名文件，覆盖写）===
        if payload.NeedSaveFile {
            filePath := fmt.Sprintf("tasks/%s/result.wav", taskID)
            if err := storage.Save(aiCtx, filePath, audioData); err != nil {
                markFailed(db, taskID, "文件保存失败")
                return err
            }
        }

        // === 完成 ===
        db.Model(&task).Updates(map[string]interface{}{
            "status":   "completed",
            "progress": 100,
            "result":   mustJSON(map[string]string{"content": content}),
        })
        return nil
    }
}
```

**3. RateLimiter 内存泄漏**

说得对，`map[string]*rate.Limiter` 只增不减，长期运行必然 OOM。修正方案用 LRU + 定期清理：

```go
// internal/middleware/ratelimit.go —— 修正版

import (
    "sync"
    "time"
    "golang.org/x/time/rate"
)

type RateLimiter struct {
    mu       sync.Mutex
    limiters map[string]*limiterEntry
    rate     rate.Limit
    burst    int
}

type limiterEntry struct {
    limiter  *rate.Limiter
    lastSeen time.Time
}

func NewRateLimiter(r rate.Limit, burst int) *RateLimiter {
    rl := &RateLimiter{
        limiters: make(map[string]*limiterEntry),
        rate:     r,
        burst:    burst,
    }
    // 每 5 分钟清理一次超过 10 分钟没访问的 limiter
    go rl.cleanup(5*time.Minute, 10*time.Minute)
    return rl
}

func (rl *RateLimiter) cleanup(interval, maxAge time.Duration) {
    ticker := time.NewTicker(interval)
    for range ticker.C {
        rl.mu.Lock()
        now := time.Now()
        for key, entry := range rl.limiters {
            if now.Sub(entry.lastSeen) > maxAge {
                delete(rl.limiters, key)
            }
        }
        rl.mu.Unlock()
    }
}

func (rl *RateLimiter) getLimiter(key string) *rate.Limiter {
    rl.mu.Lock()
    defer rl.mu.Unlock()
    if entry, ok := rl.limiters[key]; ok {
        entry.lastSeen = time.Now()
        return entry.limiter
    }
    entry := &limiterEntry{
        limiter:  rate.NewLimiter(rl.rate, rl.burst),
        lastSeen: time.Now(),
    }
    rl.limiters[key] = entry
    return entry.limiter
}
```

**4. 跨服务事件通信——确实需要补设计**

反馈里给的例子很精准：voice-service 克隆完成 → 需要通知 user-service 发 notification。阶段 2 一拆服务就会遇到。

补一个基于 Asynq 复用做事件总线的方案（不引入 Kafka，保持简单）：

```go
// internal/event/bus.go
// 事件总线：复用 Asynq，每个事件就是一个特殊类型的任务

const (
    EventVoiceCloneCompleted = "event:voice_clone_completed"
    EventDubbingExportDone   = "event:dubbing_export_done"
    EventUserRegistered      = "event:user_registered"
)

type VoiceCloneCompletedEvent struct {
    UserID  uint   `json:"userId"`
    VoiceID uint   `json:"voiceId"`
    Name    string `json:"name"`
}

// voice-service 完成任务后发布事件
func (s *VoiceService) onComplete(ctx context.Context, userID, voiceID uint, name string) {
    event := VoiceCloneCompletedEvent{UserID: userID, VoiceID: voiceID, Name: name}
    data, _ := json.Marshal(event)
    t := asynq.NewTask(EventVoiceCloneCompleted, data)
    s.queue.Enqueue(t) // 发到同一个 Redis，user-service 的 Worker 消费
}

// user-service 的 Worker 注册事件处理器
mux.HandleFunc(EventVoiceCloneCompleted, func(ctx context.Context, t *asynq.Task) error {
    var event VoiceCloneCompletedEvent
    json.Unmarshal(t.Payload(), &event)
    // 写通知
    notification := &model.Notification{
        UserID:  event.UserID,
        Type:    "task",
        Title:   "声音克隆完成",
        Content: fmt.Sprintf("「%s」已生成，可以使用了", event.Name),
    }
    return db.Create(notification).Error
})
```

这个方案的好处是**不引入新中间件**（复用已有的 Redis + Asynq），事件天然持久化、可重试。等规模真的大了再换 NATS/Kafka，接口层不用改。
